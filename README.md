# Асинхронный сервис обработки платежей

Тестовое задание для МКК «Базис». Сервис принимает платёж через HTTP API, обрабатывает его в фоне через имитацию платёжного шлюза и отправляет итог на адрес вебхука клиента.

## Что делает сервис

- Создаёт платёж с обязательным `Idempotency-Key` и возвращает `202 Accepted`, не ожидая результата обработки.
- Позволяет получить текущее состояние платежа по `payment_id`.
- Имитирует ответ шлюза за 2–5 секунд: 90% успеха и 10% ошибки на **каждой** попытке. После ошибки повторяет обработку; максимум три попытки.
- Отправляет один итоговый вебхук после `succeeded` или `failed`. Отправка также имеет три попытки.
- Требует статический `X-API-Key` для платёжных запросов и документации API. Служебный `/health` доступен без ключа.

## Главные архитектурные решения

1. **Платёж и исходящее событие сохраняются одной транзакцией.** Отдельный процесс публикует событие из `outbox` в RabbitMQ после подтверждения брокера. Поэтому API может принять платёж даже при временно недоступном RabbitMQ.
2. **Доставка — как минимум один раз.** Повторное сообщение не запускает завершённый платёж заново. После сбоя обработчик продолжает незавершённый этап по состоянию БД.
3. **Повторы двух этапов независимы.** Обработка платежа и отправка вебхука имеют отдельные счётчики: по три попытки с задержками 1 и 2 секунды через RabbitMQ. Сбой инфраструктуры не считается ошибкой платёжного шлюза.
4. **Платёж и уведомление имеют отдельные статусы.** Неудачная отправка вебхука не меняет `succeeded` или `failed`. После исчерпания попыток сообщение попадает в `payments.dlq`; автоматического разбора этой очереди нет.
5. **Получатель может убрать дубли вебхука.** Повторы несут одинаковые `event_id` и тело. Тело подписано HMAC-SHA256; в обычном режиме разрешены только безопасные HTTPS-адреса. Для локального примера разрешён отдельный получатель из Docker Compose.
6. **Идемпотентность защищена БД.** Тот же ключ с тем же содержимым возвращает исходный ответ и `payment_id`; тот же ключ с другим содержимым даёт `409 Conflict`.
7. **Доменная модель отделена от инфраструктуры.** Используем элементы DDD: `Payment` — единственный агрегат с правилами переходов, счётчиками попыток и состоянием вебхука. Он не зависит от FastAPI, SQLAlchemy, RabbitMQ или HTTP. `Outbox` служит механизмом доставки, а не отдельной бизнес-сущностью.
8. **Сценарии и адаптеры разделены.** Прикладные сервисы координируют создание, обработку и уведомление; узкие контракты репозиториев отделяют их от SQLAlchemy. HTTP-маршруты, RabbitMQ, шлюз и HTTP-клиент вебхука находятся на внешних границах. Точки запуска только собирают зависимости.
9. **Транзакция ограничена работой с БД.** Unit of work сохраняет платёж и событие `outbox` через один `AsyncSession`. Вызов шлюза, отправка вебхука и ожидание повтора выполняются вне транзакции.
10. **Проверяем поведение юнит-тестами.** Зависимости БД, брокера, HTTP, времени и случайного выбора подменяются моками; интеграционных автотестов нет. `make coverage` требует покрытия строк всего прикладного Python-кода не ниже 90% без исключения рабочих модулей. Стиль и форматирование проверяет `ruff`.

Состав окружения: FastAPI, Pydantic v2, асинхронный SQLAlchemy 2.0, PostgreSQL, RabbitMQ с FastStream, Alembic, Docker Compose. Работают API, один обработчик сообщений, отдельный публикатор `outbox` и демонстрационный получатель вебхуков.

Весь прикладной код находится в одной библиотеке `src/payment_service`. Основные файлы:

```text
.

│   │   ├── errors.py              # единый формат HTTP-ошибок
│   │   ├── schemas.py             # проверка входных данных
│   │   └── routes/
│   │       ├── payments.py        # создание и чтение платежа
│   │       └── health.py          # проверка БД и RabbitMQ
│   ├── payments/
│   │   ├── domain.py              # состояние платежа и переходы
│   │   ├── service.py             # создание, чтение, идемпотентность
│   │   ├── repository.py          # контракт хранения платежей
│   │   └── sqlalchemy.py          # ORM-модель и адаптер хранения

│   │   ├── security.py            # проверка адреса и HMAC-подпись
│   │   └── client.py              # исходящий HTTP-запрос
│   ├── outbox/
│   │   ├── event.py               # сохранённое исходящее событие
```

`main.py`, `consumer_main.py` и `outbox_main.py` запускают три рабочих процесса. `demo_receiver.py` нужен только для проверки доставки. Миграции Alembic используют ORM-модели из `payments/sqlalchemy.py` и `outbox/sqlalchemy.py`.

## Запуск

Понадобятся Docker с Docker Compose и `make`. Локальная установка Python-зависимостей не нужна.

1. Скопируйте `.env.example` в `.env` и замените учебные значения API-ключа и секрета подписи. Пример включает режим разработки и разрешает только хост `demo-receiver` для внутреннего HTTP-вебхука.
2. Запустите окружение:

   ```text
   make up
   ```

   Команда собирает контейнеры, ожидает PostgreSQL и RabbitMQ, применяет миграции и запускает сервисы.

3. Проверьте `GET http://localhost:8000/health`: код `200` означает доступность БД и брокера; `503` — недоступность хотя бы одного из них. Пример предполагает публикацию API на порту `8000`.
4. Посмотрите журналы и остановите окружение:

   ```text
   make logs
   make down
   ```

В PowerShell файл окружения можно подготовить командой `Copy-Item .env.example .env`; в оболочке Linux/macOS — `cp .env.example .env`. Не добавляйте рабочий `.env` в Git.

Если нужен внешний получатель, выключите `WEBHOOK_DEV_MODE` и укажите HTTPS-адрес с публичным сетевым назначением. Сервис проверяет адрес при приёме и перед отправкой; перенаправления не выполняются.

### Команды Makefile

| Команда | Назначение |
| --- | --- |
| `make up` | Собрать, запустить окружение и применить миграции. |
| `make down` | Остановить окружение. |
| `make logs` | Смотреть структурированные журналы всех сервисов. |
| `make test` | Запустить юнит-тесты с моками внутри контейнера. |
| `make coverage` | Проверить покрытие прикладного Python-кода: не ниже 90%. |
| `make lint` | Проверить правила кода через `ruff`. |
| `make format-check` | Проверить форматирование через `ruff`. |

Интеграционных тестов в проекте нет. Работу Docker-окружения проверяют вручную по приведённым шагам.

## Пример работы с API

Ниже — примеры HTTP-запросов. Вместо `ВАШ_КЛЮЧ` подставьте значение API-ключа из `.env`. Адрес `demo-receiver` доступен сервисам внутри Docker Compose; для него должен быть включён режим локальной разработки.

Создание платежа:

```http
POST /api/v1/payments HTTP/1.1
Host: localhost:8000
X-API-Key: ВАШ_КЛЮЧ
Idempotency-Key: example-payment-001
Content-Type: application/json

{
  "amount": "125.50",
  "currency": "RUB",
  "description": "Тестовый платёж",
  "metadata": {"order_id": "order-001"},
  "webhook_url": "http://demo-receiver:8080/webhook"
}
```

Успешное создание возвращает `202 Accepted`, `payment_id`, `status: pending` и `created_at`. Повторите тот же запрос с тем же `Idempotency-Key` — вернётся исходный ответ без нового платежа. Поменяйте любое смысловое поле при том же ключе — получите `409 Conflict`.

Получение состояния:

```http
GET /api/v1/payments/{payment_id} HTTP/1.1
Host: localhost:8000
X-API-Key: ВАШ_КЛЮЧ
```

Пока обработка не завершена, `status` равен `pending`, `processed_at` — `null`. Затем статус станет `succeeded` или, после трёх ошибок шлюза, `failed`. Отдельный `webhook_status` показывает доставку уведомления: `not_started`, `pending`, `delivered` или `failed`.

Чтобы увидеть полученный вебхук и результат проверки HMAC-подписи, откройте `make logs` и найдите записи демонстрационного получателя по `payment_id` или `event_id`. Повторное уведомление может прийти с тем же `event_id` — это допустимо при доставке как минимум один раз.

Проверки `make test`, `make coverage`, `make lint` и `make format-check` запускаются в контейнере. Автоматических интеграционных тестов нет; успешные юнит-тесты не подтверждают работу всей связки PostgreSQL, RabbitMQ и HTTP. Для ручной проверки создайте платёж по примеру, считайте его состояние по `payment_id`, затем найдите `webhook_received` в `make logs`. Если проверка `/health` возвращает `503`, проверьте состояние БД и брокера в журналах.
